# Feature Specification: Apree Workspace

**Feature Branch**: текущая локальная ветка, новая ветка не требуется.
**Created**: 2026-10-16
**Status**: Approved
**Input**: общая доска задач в визуальном стиле Apree; объём согласован пользователем в чате.

## User Scenarios & Testing

### User Story 1 — Управление задачами (Priority: P1)

Участник создаёт, открывает, редактирует и удаляет задачи. Независимая проверка: создать задачу, обновить страницу, изменить и удалить.

1. **Given** пустая доска, **When** введено корректное название, описание и приоритет, **Then** задача появляется в «Новая» и сохраняется после перезагрузки (AC-001).
2. **Given** задача существует, **When** участник открывает её, **Then** доступны полные поля, редактирование и подтверждаемое удаление (AC-002).
3. **Given** пустое или слишком длинное название, **When** отправляется форма, **Then** сохранение заблокировано с объяснением; API также отклоняет ввод (AC-003).
4. **Given** запись уже изменена другим клиентом, **When** сохраняется устаревшая версия, **Then** изменения не затираются, показан конфликт, введённый текст сохранён в форме (AC-004).

### User Story 2 — Движение работы (Priority: P1)

Независимая проверка: перевести одну задачу через все статусы и обновить страницу.

1. **Given** три колонки «Новая», «В работе», «Готово», **When** задача перемещена, **Then** карточка сразу после отпускания плавно занимает новое место без ожидания API, статус сохраняется в фоне и счётчики обновляются без мигания основного действия и фона колонок; при отказе API она возвращается к последнему подтверждённому статусу с сообщением. Быстрые повторные переносы сохраняют последнее намерение без конфликта собственных версий; откат не перехватывает более позднюю навигацию (AC-005).
2. **Given** мышь, телефон или клавиатура, **When** участник меняет статус, **Then** операция доступна перетаскиванием мышью либо явным меню статуса без обязательного drag-and-drop (AC-006).

### User Story 3 — Понятная доска (Priority: P2)

Независимая проверка: поиск по названию/описанию, фильтрация приоритета, сброс фильтров.

1. **Given** начальная загрузка, пустая доска или отказ сервера, **When** открыта доска, **Then** показаны соответственно skeleton, действие создания либо понятная ошибка с повтором; старые данные при неудаче обновления остаются видимы (AC-007).
2. **Given** ширина 360–1920 px, **When** открываются доска и форма, **Then** действия доступны, документ не имеет горизонтального переполнения; на телефоне колонки переключаются вкладками; высота колонки следует её содержимому, кнопка добавления расположена сразу за карточками либо компактным пустым состоянием (AC-008).
3. **Given** несколько задач, **When** заданы строка поиска и приоритет, **Then** применяются оба условия; при отсутствии результатов колонки плавно скрываются и остаётся сообщение со сбросом фильтров; после сброса доска плавно возвращается (AC-009).

### Edge Cases

Пробельное название; Unicode; описание до 5000 символов; название до 160 символов; неизвестные поля/статусы; отсутствующий UUID; двойной клик; одновременные PATCH и DELETE; потеря сети; повтор загрузки; длинный непрерывный текст; попытка закрыть несохранённую форму.

## Requirements

### Functional Requirements

- FR-001: три фиксированных статуса и три приоритета: низкий, средний, высокий.
- FR-002: CRUD с проверкой ввода, подтверждением удаления и устойчивым хранением (AC-001–004).
- FR-003: перенос между статусами; внутри колонки стабильная сортировка по дате создания от новых к старым (AC-005–006).
- FR-004: загрузка, пустота, отказ, повтор и сохранение пользовательского ввода при ошибке (AC-007).
- FR-005: адаптивность, читаемые подписи без обрезания, видимый фокус, управление без мыши; prefers-reduced-motion отключает пространственные анимации (AC-008).
- FR-006: поиск по названию/описанию и фильтр приоритета (AC-009).
- FR-007: интерфейс использует понятные продуктовые формулировки и названия действий.

### Key Entities

Task: идентификатор, название, описание, приоритет, статус, версия, время создания и обновления. Доска общая; аккаунты и разграничение доступа не входят в согласованный объём.

## Success Criteria

- SC-001: путь создания → просмотра → изменения → переноса → перезагрузки → удаления проходит без потери данных.
- SC-002: все действия доступны на 360 px и 1440 px, клавиатурой и touch-эмуляцией.
- SC-003: неверный ввод, устаревшая версия и недоступность сервера не приводят к незаметной потере изменений.
- SC-004: инструкция позволяет запустить приложение и миграции на чистой машине с Node.js и Docker.

## Assumptions

Локальная работа в доверенной среде; без внешнего размещения до отдельного решения о доступе. Перенос добавляет задачу в естественный порядок целевой колонки, ручное ранжирование не требуется.
