# Порядок разработки

## 1. Понять продукт

Прочитай [описание продукта](project-brief.md). Если оно не заполнено, используй [стартовый запрос](../START-HERE.md). Определи пользователей, проблему, границы первой версии и ограничения.

## 2. Описать результат через SDD и BDD

Используй `speckit-specify`. Документы функции находятся в `specs/<номер>-<название>/`. Критерии приёмки получают устойчивые ID, например `AC-001`; сценарии проверяют их через Given / When / Then.

Опиши основной путь, ошибочный ввод, недостаточные права и применимые отказы. Не добавляй сценарии без связи с задачей. Неопределённость, влияющую на поведение, обсуди с пользователем. Согласуй результат и критерии перед реализацией существенной новой функциональности.

## 3. Спроектировать решение

Используй `speckit-plan`. Уточни [System Design](architecture/system-design.md) на уровне проекта; детали функции сохрани в её плане и контрактах. Для значимого выбора создай [ADR](adr/README.md). Для локального исправления отдельный архитектурный документ не нужен.

Заполни [команды проекта](commands.md) реальными командами выбранного стека. Добавь CI для подходящих тестов, статических проверок и сборки. Не объявляй проверки выполненными до фактического запуска.

## 4. Разбить на проверяемые задачи

Используй `speckit-tasks`. Свяжи задачи с требованиями и сценариями. Для существенной логики сначала поставь тестовую задачу, затем реализацию. Включи интеграционные проверки там, где важны БД, сеть, авторизация, повторные запросы или конкурентные события.

При риске противоречий используй `speckit-analyze`. Устранение несогласованных требований предшествует реализации.

## 5. Реализовать небольшими шагами

Используй `speckit-implement` и [правила тестирования](testing.md). Зафиксируй провал нужного теста по ожидаемой причине, реализуй минимальное поведение, затем улучши код при зелёных тестах. Документы и контракты обновляй при изменении поведения.

## 6. Проверить и завершить

Выполни затронутые проверки. Передай законченный снимок собственного кода независимому senior-ревьюеру по `AGENTS.md`; не меняй его во время ревью. Исправь подтверждённые дефекты и верни исправления ревьюеру.

Используй `speckit-converge` для сверки реализации со спецификацией. Проверь [критерии готовности](definition-of-done.md). Сообщи, что изменилось, какие проверки выполнены, охват ревью и ограничения.

Commit, push и деплой выполняются только по прямой команде пользователя. Skills и workflow не отменяют это правило.
