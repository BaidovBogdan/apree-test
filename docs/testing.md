# BDD и TDD

BDD уточняет ожидаемое поведение. TDD помогает реализовать и безопасно изменять логику. Markdown и `.feature` сами по себе не запускают проверки.

## BDD: от требования к сценарию

1. В `spec.md` назначь критерию ID: например, `AC-001`.
2. Опиши Given / When / Then с конкретным наблюдаемым результатом.
3. Добавь применимые негативные сценарии: неверный ввод, права, отказ зависимости, повторное действие или гонка.
4. Свяжи сценарий с автоматическим тестом либо явно указанной ручной проверкой.

Встроенного формата acceptance scenarios Spec Kit достаточно. Если нужен отдельный Gherkin-файл, скопируй [шаблон](templates/acceptance.feature) в папку функции и синхронизируй его со спецификацией. Не заводи два независимых описания поведения. Пример — в [examples/cancel-order](../examples/cancel-order/README.md).

BDD-runner добавляй только при пользе для команды. Можно назвать обычный тест по сценарию и использовать Arrange / Act / Assert. Если runner есть, отсутствующий или pending step не считается успешным тестом.

## TDD: Red → Green → Refactor

- **Red:** напиши тест и запусти. Он должен провалиться по ожидаемой причине, а не из-за сломанной установки или ошибки импорта.
- **Green:** реализуй минимальный код, который проходит тест. Запусти его снова.
- **Refactor:** улучши структуру, сохрани поведение и повтори затронутые проверки.

Используй TDD для сложной логики, важных контрактов и рисков регрессии. Для воспроизводимого дефекта сначала добавь регрессионный тест, если это соразмерно риску. Для текста и тривиального форматирования тест не нужен.

## Уровни проверок

| Уровень | Что подтверждает |
| --- | --- |
| Unit | Локальные правила и граничные значения |
| Integration / contract | Взаимодействие с БД, API, очередью и схемами |
| E2E | Несколько критичных пользовательских путей |
| Ручная проверка | То, что пока не автоматизировано; шаги и результат фиксируются |

Моки не подтверждают совместимость с реальной внешней системой. Отказы, таймауты и повторные события проверяй там, где это существенно. Используй синтетические данные, изоляцию окружения и воспроизводимые условия.

## Отчёт

В `specs/<функция>/verification.md` по [шаблону](templates/verification.md) запиши: критерий → тест/шаги → выполненная команда → фактический результат. Для незапущенного теста укажи причину. Не помечай требование выполненным только потому, что AI написал тест.
