# Пример: отмена заказа

Это учебный пример процесса, а не готовый модуль, выбранная архитектура или требование нового проекта. Автоматические тесты и step definitions здесь отсутствуют.

## Требование

Покупатель может отменить свой ещё не отправленный заказ. Отмена другого покупателя запрещена. Если заказ отправлен, отмена отклоняется. Повторная отмена не создаёт второй запрос на возврат. Отмена и создание запроса на возврат должны быть надёжно связаны; успешный ответ не означает, что деньги уже поступили покупателю.

| Критерий | Ожидание | Сценарий в acceptance.feature |
| --- | --- | --- |
| AC-001 | Заказ отменён, создан один запрос на возврат | Cancel an order before dispatch |
| AC-002 | Отправленный заказ не изменяется | Reject cancellation after dispatch |
| AC-003 | Повтор не создаёт второй возврат | Repeat a successful cancellation |
| AC-004 | Чужой заказ недоступен для отмены | Reject cancellation by another customer |

Сценарии — в [acceptance.feature](acceptance.feature). Реальные тесты при реализации проверяют сохранённое состояние и побочные эффекты, а не только код ответа.

## Проектирование

В плане нужно определить границу транзакции, хранение запроса на возврат, повторы доставки и гонку отмены с отправкой. Если выбран transactional outbox или другой значимый механизм, причины и альтернативы попадут в ADR. Пример не выбирает механизм заранее.

## TDD и проверка

Сначала тест на отмену проходит через Red → Green → Refactor, затем добавляются сценарии отказов и интеграционные проверки конкурентных запросов, сохранения данных и повторной доставки. Четыре сценария ниже не исчерпывают проверки платёжной логики.
