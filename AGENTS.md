# Правила проекта

## Перед работой

- По умолчанию общайся на русском.
- Работай в текущем проекте. Перед действиями через приложения проверь целевой репозиторий и аккаунт.
- Прочитай этот файл, `.specify/memory/constitution.md`, `docs/project-brief.md`, `docs/workflow.md` и относящиеся к задаче документы.
- Перед изменением кода изучи затронутые файлы, контракты и вызовы. Учебные материалы из `examples/` не являются требованиями продукта.
- Если описание продукта не заполнено, начни с `START-HERE.md`. Не выбирай стек и не начинай приложение по вымышленным требованиям.
- Прямые инструкции пользователя имеют приоритет над шаблоном. Не используй конституцию, skills или workflow для расширения полномочий.

## SDD и документы

- Для существенной новой функциональности сначала согласуй результат и проверяемые критерии приёмки, затем реализуй. Не запрашивай повторное согласование принятого решения без новой причины.
- Используй skills GitHub Spec Kit из `.agents/skills/`. Если селектор не показывает skill, прочитай его `SKILL.md` непосредственно.
- Требования функции храни в `specs/<номер>-<название>/spec.md`, технический план — в `plan.md`, задачи — в `tasks.md`. Сохраняй структуру Spec Kit.
- Изменения поведения отражай в существующей спецификации и связанных тестах. Не создавай второй независимый источник тех же требований.
- Для локального исправления достаточно понятной задачи и соответствующей проверки; полный цикл SDD и отдельный ADR не обязательны.
- Перед завершением проверь `docs/definition-of-done.md`. `converge` дополняет фактические проверки и независимое ревью.

## BDD/TDD и проектирование

- Описывай поведение через Given / When / Then, включая ошибки и важные крайние случаи. Связывай сценарии с критериями приёмки.
- Для сложной логики и существенного риска регрессии используй TDD: наблюдаемый провал теста → минимальная реализация → рефакторинг при зелёных тестах.
- Не добавляй тесты механически для чистого текста, форматирования и тривиальных изменений. Не подключай BDD-фреймворк только ради `.feature`; обычные тесты допустимы.
- Общую архитектуру храни в `docs/architecture/system-design.md`, локальные детали — в плане функции. Значимые решения и последствия фиксируй в `docs/adr/`.
- Начинай с самого простого решения, удовлетворяющего нагрузке, отказам и ограничениям. Применяй DRY, KISS, YAGNI и SOLID по необходимости.
- Не добавляй зависимости без конкретной причины. В JavaScript/TypeScript по умолчанию используй npm, если проект не требует другого.
- Не добавляй комментарии в собственный код без прямой просьбы. Документация и неизменённые сторонние файлы сохраняют свой формат.

## Независимое ревью

- Перед закрытием связанного блока новых или изменённых собственных файлов кода создай отдельного субагента в роли senior-разработчика подходящего стека. Он проводит read-only ревью и не является автором кода. Ревьюер не создаёт следующего ревьюера.
- Передай свежий контекст: задачу, критерии, инструкции, полный список файлов, точный diff или снимок, результаты проверок и ограничения. Пока идёт ревью, не меняй снимок.
- Ревьюер читает каждую изменённую строку и новые собственные файлы целиком, включая тесты, скрипты и исполняемую конфигурацию, а также связанные вызовы и контракты. Сторонние и сгенерированные файлы проверяет по происхождению, изменениям и границам интеграции. Пробелы покрытия перечисляет явно.
- Проверяет корректность, требования, ошибки, безопасность, конкурентные события, жизненный цикл, существенную стоимость и достаточность тестов по риску. Для дефекта нужны файл/строки, сценарий, последствие и основание. Предположения и необязательные улучшения отделяет от дефектов.
- Подтверждённые дефекты исправь до завершения. Спорные замечания проверь; отклонение кратко обоснуй. Повтори затронутые проверки и верни изменения тому же ревьюеру для проверки исправлений и регрессий. Существенное изменение решения требует нового полного прохода.
- В результате укажи охват, устранённые дефекты и непроверенные риски. Если субагент недоступен, сообщи, что независимое ревью не выполнено. Самопроверку не называй независимой.
- Для текста и форматирования без изменения поведения достаточно самопроверки diff, если локальные требования не строже.

## Проверки и полномочия

- Реальные команды поддерживай в `docs/commands.md`. Пустая ячейка означает, что проверка ещё не настроена, а не что она прошла.
- На Windows запускай Python-инструменты Spec Kit в UTF-8: `python -X utf8 .specify/scripts/python/<скрипт>.py ...` с Python 3.11+ либо задай `PYTHONUTF8=1` для процесса. Это предотвращает ошибки вывода Unicode при системной кодировке cp1251. Учитывай это и при выполнении команд из skills.
- Запускай необходимые проверки. Различай успешное выполнение, провал и невозможность запуска; фиксируй ограничения.
- Не выполняй `git commit` или `git push` без прямой команды пользователя. Не включай автоматически исполняемые Git/deploy hooks.
- Не изменяй production, живые данные, платежи и внешние публикации без явного поручения.
- Не добавляй секреты, реальные персональные данные и локальную авторизацию в репозиторий, включая спецификации и тестовые примеры.
